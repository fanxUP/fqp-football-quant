# 36 模块化架构与可升级边界

## 1. 建设目标

FQP 的模块化目标是把系统从“功能堆叠型项目”升级为“模块化、可插拔、可灰度升级、可扩展功能面板”的长期工程。后续新增玩法、数据源、模型、报表、AI Agent、前端页面时，不应大面积改动核心代码。

系统必须满足：

1. 每个业务能力独立成模块，有清晰输入、输出、表结构、接口、任务、权限。
2. 新模块通过模块注册表接入，不直接写死在导航、路由、任务调度和推荐流程里。
3. 前端功能面板通过 Panel Registry 注册，支持启用、隐藏、排序、权限控制。
4. 后端模块通过统一 Module Contract 暴露 API、任务、事件、模型能力和依赖关系。
5. 数据库迁移按模块归档，禁止所有表混在单一 SQL 文件长期维护。
6. 多 Agent 按模块分工，Codex 修改某一模块时必须知道影响范围。
7. 所有模块必须有测试、验收、回滚和版本号。

## 2. 总体模块边界

系统分为 16 个一级模块：

| 模块编码 | 模块名称 | 主要责任 | 可独立升级 |
|---|---|---|---|
| core_official | 官方数据中台 | 官方赛程、玩法、SP、赛果 | 是 |
| data_governance | 数据治理 | 球队映射、数据质量、源可信度 | 是 |
| season_team | 赛季球队库 | 赛季、赛事、积分、球队画像 | 是 |
| player_lineup | 球员阵容库 | 球员、身价、首发、替补 | 是 |
| injury_availability | 伤停可用性 | 伤病、停赛、出战成疑、轮休 | 是 |
| stadium_weather | 球场天气旅行 | 球场、经纬度、天气、疲劳 | 是 |
| motivation_tournament | 战意赛制博弈 | 晋级、保级、避强队、半区路径 | 是 |
| feature_store | 特征快照库 | 比赛多维特征快照 | 是 |
| model_research | 模型研究 | Poisson、Dixon-Coles、Shin、Kelly | 是 |
| model_committee | 模型委员会 | 多模型投票、一致性、不确定性 | 是 |
| recommendation | 推荐引擎 | 候选池、EV、票单、资金分配 | 是 |
| ticket_review | 实票复盘 | 上传票据、结算、偏差、复盘 | 是 |
| pool_lottery | 传统足彩 | 胜负14、任九、组合覆盖 | 是 |
| backtest | 回测中心 | walk-forward、ROI、Brier、回撤 | 是 |
| agent_codex | Codex 多 Agent | 开发、审查、修复、任务编排 | 是 |
| ops_admin | 运维后台 | 监控、报警、审计、备份 | 是 |

## 3. 模块接入四件套

每个模块必须至少具备四件套：

```text
1. module_manifest.yaml     模块清单
2. database_migrations/     模块数据库迁移
3. api_contract.yaml         模块 API 契约
4. acceptance_checklist.md   模块验收清单
```

推荐扩展件：

```text
5. jobs.yaml                 模块定时任务
6. events.yaml               模块事件定义
7. panels.yaml               模块前端面板
8. permissions.yaml          模块权限定义
9. codex_tasks.yaml          Codex 任务模板
10. rollback.md              回滚说明
```

## 4. 模块之间的依赖规则

允许的依赖方向：

```text
官方数据中台 -> 数据治理 -> 赛季球队/球员/伤停/天气/战意 -> 特征快照 -> 模型 -> 推荐 -> 实票复盘/回测
```

禁止的依赖方式：

```text
推荐模块直接抓第三方数据
模型模块直接写实票表
前端面板直接查询原始采集表
Agent 模块绕过任务队列直接改生产数据
回测模块使用赛后字段生成赛前特征
```

每个跨模块调用必须通过：

```text
API Contract
Event Bus
Feature Snapshot
Read Model View
```

## 5. 升级维护原则

1. 小改动优先局部模块升级。
2. 新玩法优先新增模块，不要污染竞彩足球核心模块。
3. 新数据源必须先进入数据治理模块，再进入特征快照。
4. 新模型必须先在 model_research 模块回测，通过后才能进入 model_committee。
5. 新前端功能必须通过 Panel Registry 注册，不允许硬编码导航。
6. 所有数据库变更必须有版本号和回滚脚本。
7. Codex 每次任务必须绑定模块名、影响文件、测试命令和回滚说明。

## 6. 模块化落地验收

| 验收项 | 标准 |
|---|---|
| 模块注册表 | 所有一级模块完成注册 |
| 面板注册表 | 核心面板可按权限启停 |
| API 契约 | 每个模块有边界接口 |
| 数据库迁移 | 新增模块 SQL 独立归档 |
| Codex 任务 | 任务可按模块分配 |
| 前端扩展 | 新增面板无需改核心布局 |
| 回滚 | 模块升级失败可关闭或回退 |
| 测试 | 每个模块有独立验收清单 |
