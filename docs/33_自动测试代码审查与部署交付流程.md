# 33. 验证、审查与部署交付

## 保留规则

1. 按任务授权选择本地检查，并记录命令、环境、提交、退出码和未运行项。原因：不同变更需要不同证据，不能用空白清单代表通过。
2. 合并准备核对目标提交对应的实际 CI，失败项修复或明确阻断。原因：其他提交的绿灯不能证明本次改动可合并。
3. 涉及赔率、预测、票据和收益时检查快照、时间边界、来源与审计。原因：这些信息决定结果能否追溯，真实与模拟收益不能混算。
4. 迁移按现有执行器检查顺序、校验和、权限及兼容性，恢复方案按实际能力说明。原因：当前没有覆盖全部迁移的 down SQL 或通用迁移回滚测试。
5. 发布使用相应环境入口；服务器 `deploy.sh` 默认 plan，apply 需要匹配目标提交的发布证据。原因：脚本检查质量、迁移副本演练、回退审查、受保护 HTTP 烟测及备份。
6. 发布后核对就绪、关键业务和已部署版本，并保留回退材料。原因：代码拉取成功不等于服务和数据正常。
7. 回退时分别说明代码、配置、模型和数据库处理。原因：当前服务器脚本回退代码并保留已应用的兼容性迁移，不执行破坏性 SQL 回滚。
8. 仅允许发布器明确识别的 Vite/Vitest 开发依赖闭包更新，并在代码回退时按旧锁文件恢复依赖。原因：仅回退源码却保留新依赖可能使旧版前端无法重建。

## 服务器发布停机前门禁

1. 停止服务前，先核对目标 SHA、干净的 `main` 工作树、发布证据 JSON 的字段/时效/目标 SHA、回退 SHA、服务就绪状态、磁盘空间和迁移清单。回退 SHA 应取当前 checkout 的 `HEAD`，并与服务器 `.runtime/release-id` 开头的 40 位 SHA 一致；不一致时先查明当前运行版本。原因：证据格式、环境或版本条件不合格应在影响线上服务前被发现。
2. 临时 sudo 辅助脚本必须按 `deploy.sh` 实际发出的完整参数逐项匹配，包括 `sudo` 选项、`--` 分隔符、`env` 参数和迁移命令参数；用无副作用的权限检查覆盖发布需要的每种调用，并在停服前完成验证。原因：命令参数不一致会使权限规则拒绝真实迁移命令。
3. 尽可能在停服前完成目标版本的依赖安装、前端构建和迁移计划/副本演练；无法提前完成的检查必须明确记录其影响和回退路径。原因：检查失败若发生在停服后会扩大中断时间。
4. 只有全部停机前门禁通过后才停止服务。应用失败时确认脚本已恢复原 SHA、服务已启动且 readiness 正常，再决定是否重试；不得绕过失败继续发布。原因：自动回滚需要用实际健康检查确认恢复完成。
5. 发布结果和运行证据保存在 Git 工作树之外，并同时记录目标 SHA、部署时间和服务器 release ID。原因：运行时记录不应形成与代码无关的脏改动，同时仍需能追溯它对应的版本。
6. 发布后核对服务状态、`/health/ready`、关键路径和版本接口；版本接口的 release ID 必须指向本次目标 SHA。原因：进程存活或首页可访问不能证明新版本实际生效。

### 本次发布复盘（2026-10-22）

第一次 apply 因临时 sudo 辅助脚本的迁移命令参数与 `deploy.sh` 实际调用不一致而失败。部署脚本自动回退到原提交并恢复服务；数据库迁移未执行。修正辅助脚本后再次发布成功，目标提交与服务器 release ID 一致，健康检查通过。此事说明临时权限脚本也属于发布代码路径，必须在停服前按真实 argv 做预检。

当前 `deploy.sh --plan` 要求干净的 `main` 工作树和 `.venv/bin/python`，会 fetch `origin/main` 并要求目标 SHA 与远端 `main` 一致，再检查依赖变更并输出计划；它不会验证 apply 所需的发布证据、sudo 命令契约、服务状态或构建与迁移计划。当前 apply 路径还在停止应用服务后执行目标版本 checkout、前端依赖安装/构建和迁移计划。因此，本节是发布操作门禁，并不表示脚本已经自动执行全部门禁；将这些可提前完成的步骤移到停服前仍是部署脚本的后续改进项。

## 当前 CI 内容

事实来源：`.github/workflows/ci.yml`。

| 范围 | 已配置步骤 |
| --- | --- |
| Python | Python 3.14，Ruff 检查/格式，Mypy |
| Pi bridge | Node 24，`npm ci --ignore-scripts`，类型检查和测试 |
| 前端 | `npm ci`、类型检查、Vitest、构建 |
| 数据库与后端测试 | PostgreSQL 16，按序迁移，独立 Pi/特征/观测测试库；另一个同版本临时 CI 集群提供 P106/审计库及受限 fqp 角色；Pytest 覆盖率 |

后端覆盖率步骤显式收集`tests`和`apps/backend/src`，避免后端服务/路由旁的测试遗漏。`FQP_P106_TEST_DATABASE_URL`和`FQP_AUDIT_TEST_DATABASE_URL`仅指向临时CI集群的loopback测试库；管理员负责建表，权限断言使用非超级用户、无管理权限的`fqp`。原因：旧CI主集群的同名账号是初始化管理员，不能拿它证明应用权限受限。该临时集群只用于CI，不是新增产品数据库或修改统一数据架构。

完整Pytest成功后，再检查实际JUnit：预测run、训练样本、预测/回测/通用任务、实票、模型工件、污染审计和首页计数九个关键数据库模块，以及后端源码目录中的全部测试模块都必须收集且无skip/error/failure。其他明确可选的测试仍按原规则处理。原因：套件退出码0也可能掩盖缺连接导致的跳过。

这里描述配置内容，不代表GitHub已执行新工作流；本机隔离演练与真实GitHub CI分别记录。旧的独立 Risk gate CI、全部任务 dry-run、统一 15 分钟回退承诺没有对应实现。
