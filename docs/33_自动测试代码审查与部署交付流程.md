# 33. 验证、审查与部署交付

## 保留规则

1. 按任务授权选择本地检查，并记录命令、环境、提交、退出码和未运行项。原因：不同变更需要不同证据，不能用空白清单代表通过。
2. 合并准备核对目标提交对应的实际 CI，失败项修复或明确阻断。原因：其他提交的绿灯不能证明本次改动可合并。
3. 涉及赔率、预测、票据和收益时检查快照、时间边界、来源与审计。原因：这些信息决定结果能否追溯，真实与模拟收益不能混算。
4. 迁移按现有执行器检查顺序、校验和、权限及兼容性，恢复方案按实际能力说明。原因：当前没有覆盖全部迁移的 down SQL 或通用迁移回滚测试。
5. 发布使用相应环境入口；服务器 `deploy.sh` 默认 plan，apply 需要匹配目标提交的发布证据。原因：脚本检查质量、迁移副本演练、回退审查、受保护 HTTP 烟测及备份。
6. 发布后核对就绪、关键业务和已部署版本，并保留回退材料。原因：代码拉取成功不等于服务和数据正常。
7. 回退时分别说明代码、配置、模型和数据库处理。原因：当前服务器脚本回退代码并保留已应用的兼容性迁移，不执行破坏性 SQL 回滚。
8. 仅允许发布器明确识别的 Vite/Vitest 开发依赖闭包更新，并在代码回退时按旧锁文件恢复依赖。原因：仅回退源码却保留新依赖可能使旧版前端无法重建。
