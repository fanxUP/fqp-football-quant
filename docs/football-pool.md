# 传统足彩彩池

`/pool` 为官方14场、任九研究方案工具，复用统一 PostgreSQL 和完整预测组，不创建资金流水。服务器部署时前后端须同批更新至 `football-pool/v2`；旧 `monte_carlo` 合同已移除。

## 数据与时间

- 官方玩法使用 `t14c` / `r9`，期次唯一键为 `(game_type, issue_no)`，任九必须有独立官方记录，不能复制14场截止时间。
- `saleEndTime`、`lotterySaleEndtime`、`lotterySaleEndTime` 为可识别的停售字段；`estimateDrawTime` 仅是预计开奖，不能代替停售。截止、开售、`onSale` 冲突或未知时显示研究数据，不生成可用组合。
- 赛程与预测的无时区时间按北京时间解释；审计列 `model_predictions.created_at` 遵循项目统一 UTC 存储。运行连接使用既有 UTC 配置，不能把旧主机本地审计时间当 UTC 回填。
- 比赛仅按唯一的主客队及精确开赛时间映射；已有本地FK也重新核对对阵。供应商ID单独写入 `source_match_id`，歧义保持待核实。
- 每个玩法以分析时刻、官方停售、开赛时间的最早值为边界。先过滤 `predict_time`、group创建／完成、run创建／完成时间，再按逻辑模型取最新完整组；校验 manifest、工件绑定、完整三项、独立模型用途和概率。
- 历史模型版本按留存组重建，不受今天 active 标记影响，也不声称恢复了原始模型选择策略。无完整来源的 legacy 不能证明同次预测，保留缺口，不按选项拼接。
- 只解析选中期次的两种玩法对阵，预测批量读取两次SQL，不对每注查库。读操作使用重复读只读事务。

## 计算与缺项

输入向量复用共享 SPF 校验。合法0保留，布尔、缺项、非有限、越界或超容差总和拒绝；容差内舍入仅在计算副本归一化，原向量及合计保留。

整注全中为选项概率乘积，期望命中场次为选项概率之和。不同单注去重后相加得到至少一注全中概率；14场至少13场事件对每注与改动一个结果的赛果取并集，避免重复计数。所有数值均以输入概率和场次独立为假设，不证明实际模型效果或盈利。

14场要求14场合格预测；任九要求至少9场。任九按最大结果概率、熵、官方场序稳定排序，可固定／排除场次。复式展开、展示、快照和导出使用相同九场身份。允许0胆，胆只表示单选。市场、天气、伤停等缺项由模型自己的输入合同处理，彩池不另设全局硬门槛。

单注金额只从 `configs/pool_rules.yaml` 读取。每个玩法分别使用2至10000元偶数预算；候选选项范围由策略决定，使用堆按联合概率生成前K注，只对该固定候选集合的全中目标排序，不宣称13场覆盖或任九选场全局最优。

## 接口与留存

- `GET /api/pool/issues`：最近100份官方玩法期次及窗口状态。
- `GET /api/pool/analyze?budget=256&strategy=balanced&issue_id=...&pinned_orders=...&excluded_orders=...`：结构化就绪／缺口及完整组合。`issue_id` 优先解释为本地ID，其次官方期号；页面始终提交本地ID。省略时优先最新在售期次，否则最近记录，不因缺预测偷偷退回旧完整期次。
- `POST /api/pool/issues/{issue_id}/generate-combinations`：保留旧路径，返回新分析合同，不写库。
- `GET /api/pool/sample`：明确标注合成示例，不能保存成官方方案。
- `POST /api/pool/plans`：提交分析返回的 parameters 和 input_hash。服务器重新读取并计算，来源变化返回409；只在显式保存时写 `football_pool_combinations`，重复内容返回原ID。
- `GET /api/pool/plans`：最近50份保存记录。
- `GET /api/pool/plans/{id}`：校验完整快照摘要，返回原快照和 stale；当前来源变化不改写旧记录。

快照保留两种玩法的截止与证据、全部候选向量、实际九场身份、模型版本、run/group/hash、参数、完整单注、计算版本、假设和输入摘要。snapshot_hash 规范为现有 canonical JSON SHA-256，排除快照摘要本身及随请求变化的展示时钟（generated_at、data_as_of、rx9.data_as_of）；输入身份与完整输出仍被覆盖。数据库触发器禁止更新或删除 v2 快照，新结果另存版本。

页面可导出完整 JSON，预览10注不代表完整清单。保存表的注数／成本为首个可用玩法的比较摘要（优先14场，其次任九），不是两玩法合计购买金额；完整两方案成本均在 JSON 中。奖金、ROI和EV不推算，保持未知。传统足彩实票及浮动奖结算仍是后续独立任务，沿用现有账本而非新增钱包。

## 117迁移与恢复

新安装和已有安装按项目迁移顺序执行 `117_pool_identity_and_snapshots.sql`，不修改已发布迁移。它保留原期次ID、比赛和组合引用，移除 issue_no 单列唯一约束，增加玩法＋期号唯一索引、精确对阵索引、外部ID列和快照保护。没有另一玩法原始证据的旧期次不会被复制；旧记录 source_game_type 为空，保留数据但不作为已核实玩法的可用方案，须由新版官方采集确认。无明确官方停售字段的旧值留存在 raw_json._pool_correction_v1，停售清空待核实；有显式但冲突的值仍由读取合同阻断。

迁移事务锁等待最多2秒、语句最多15秒；任一失败整体回滚。索引创建会阻碍写入，生产发布前须按实际表规模选短暂停采窗口，检查是否有额外自建 issue_no 唯一索引或依赖旧唯一约束的外键，先在数据副本验证；不要在失败后直接放宽超时。执行前核验期次数、玩法分布、fixture/方案引用和 raw_json 留存情况。

本轮只在本机专用隔离数据库演练，未连接生产。以后发布使用项目既有发布与恢复策略：迁移前保留必需恢复材料；失败自动事务回滚；应用回退只能恢复到读取新唯一键的兼容版本。已经新增同号不同玩法后，旧 `ON CONFLICT(issue_no)` 写入程序不能直接恢复运行。不要为恢复旧唯一约束删除另一玩法；需要回到迁移前结构时，暂停写入后恢复迁移前完整数据库与匹配代码。快照触发器保护的是项目应用数据，不替代数据库备份。
