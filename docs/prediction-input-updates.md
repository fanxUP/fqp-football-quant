# 观测更新待办

P105/02 为 P104 的观测写入提供 PostgreSQL dirty-match 待办。显式入口位于
`scripts.prediction_input_updates`，不自动启动任务，不改变现有预测或建议发布流程。

## 事实与通知

迁移109在 `observation_checks` INSERT 后触发通知，在原事务中更新
`prediction_input_dirty_matches`。同值刷新改变时效，失败/额度耗尽与恢复改变可用状态，
这些回执均递增该场比赛的 `input_version`。任一通知失败会使同事务的事实写入失败；
调用者应整体回滚。未提交的事实不会被其他连接领取。

版本是更新围栏，不是特征内容哈希或模型版本。同场多个事件可以合并为一次最新版本消费；
需要逐条证据时读取 P104 不可变历史。109不回填旧观测，不声称历史已全部通知。
`feature_batches` 不触发通知，避免构建批次后再次唤醒自己。

## 领取、计算、完成

1. 由现有任务入口调用 `claim_input_updates(conn, consumer_key="prediction-refresh/v1")`。
   消费者键来自有界的内部配置；不要按用户、请求或运行生成新键。
   默认每批8场，允许1–32场；默认租约120秒，允许10–900秒。
2. 及时提交领取事务，释放短锁，再单独捕获/提交 P104 cutoff，并计算确切批次。
   不要在领取连接持有未提交写入时调用 cutoff capture，也不要在数据库锁内训练或请求来源。
   此 API 不续租；选用满足单场有界计算时长的租约，超时由后续任务重领。
3. 在新的短事务调用 `complete_input_update(conn, claim, publish)`。
   该函数锁定输入头与该消费者进度，验证当前输入版本、租约、token，随后执行受信任的
   **仅数据库写入**回调，并将结果引用、唯一消费回执和完成位置一并提交。
   回调接收 `(conn, claim)`，返回最多16KiB的 JSON 对象，例如确切 batch/revision ID。
4. 回调不能 commit/rollback、写入观测、进行网络/缓存调用或调用资金/票据/结算。
   此约束面向受控内部代码，不是任意插件的沙箱。回调结束后再次检查版本和租约。
   回调失败、返回值不合法、租约失效等会回滚该函数 savepoint 内的写入；外层事务由调用者管理。
5. 已有相同 `(consumer_key,match_id,input_version)` 回执时，直接返回原引用和
   `already_completed`，不再调用回调。回执只能追加，不能覆盖历史结果。

不同消费者有独立完成位置。领取采用 `FOR UPDATE SKIP LOCKED`，同消费者并发工作者
不会在有效租约内领取同一场。崩溃后的租约可到期重领，旧 token 不能完成或释放新租约。
如果处理期间来源更新，完成操作抛出 `InputUpdateSuperseded`；新版本仍待消费。
调用者可在回滚/结束当前事务后调用 `release_input_update`，只释放自己的 token，
再交给现有任务的有界重试/退避机制。API 不自循环重试。

## 复用与边界

- `ai_job_runs` 继续负责任务运行记录，既有调度入口后续调用本模块；本批不新增调度器、
  Redis队列或服务。
- 启动恢复队列按 boot/window 管理任务，且函数自行提交；它不适合直接嵌入事实事务。
  报表 `model_performance_dirty_matches` 仍服务自己的消费者，本模块沿用其数据库失效模式，
  补足输入版本、独立消费位置和租约。
- 本批只通知实际追加的观测回执。未来发布时间到达、自然过期、官方赛程/销售/赔率变化
  的唤醒与版本管理尚未接入；不能声称已覆盖所有预测失效原因。
- 输入版本不替代 P104 cutoff/batch，也不证明结果来自该批次。受控消费者须绑定确切引用；
  持久建议修订、旧建议版本失效以及停售/开球门槛将在后续 P105 集成完成。
- 本批回执不是预测 run 或建议发布。市场参考的非独立身份仍由输入策略保留；无提升预测
  准确率、无资金/结算幂等改动。
- Redis/HTTP等外部副作用不得进入完成事务。缓存仅在数据库提交后刷新；失败不能撤销
  已提交事实，读取者还需版本校验以防旧建议复活，该读取集成尚未完成。

## 迁移、权限与恢复

109只新增三张空表、约束、索引和观察回执触发器，不改107/108历史或已有业务记录。
空表建索引；触发器加锁受 `lock_timeout=2s` / `statement_timeout=15s` 限制，
超时应中止迁移，不能自动扩大超时。源写者按既有 stream advisory lock 再锁输入头；
消费者按输入头再锁消费进度，回调禁止写观测以防锁顺序逆转。

通知触发器由迁移角色拥有，`SECURITY DEFINER SET search_path=pg_catalog`，只使用固定的
`public` 关系名，撤销 PUBLIC 调用。来源写者继续只有原来的历史 SELECT/INSERT，
无需队列表 UPDATE 权限。读者只需三表 SELECT；受信任消费者需要头表 SELECT/UPDATE
（行锁需要UPDATE权限）、进度表 SELECT/INSERT/UPDATE、回执表 SELECT/INSERT。
它们不因此获得事实 UPDATE/DELETE 或回执 UPDATE/DELETE。生产角色授权属于后续切换，
不能使用本地CI初始化脚本操作生产。

空新表允许109的 guarded down；任一新表非空即拒绝删除。上线后回滚应用并保留表、
触发器和历史位置；不得为回退应用清空队列。备份/恢复需一起保留 P104 事实、三表数据、
索引约束和触发器。独立副本 dry-run 和实际恢复证据准备齐全后才可进入生产迁移评审。


## 本地验证入口

新增回归位于 `tests/test_computation/test_prediction_input_updates_postgres.py`，复用
P104的严格DSN及数据库标记检查；不配置隔离数据库时跳过，不使用应用的DATABASE_URL。
CI仍按现有数字顺序加载SQL迁移，再运行 `init_observation_test_db.sh` 初始化隔离副本。
该脚本在检测到109表时创建无登录消费者角色并显式授权。
结构副本使用 `--no-privileges`，因此必须显式恢复通知函数的PUBLIC撤权；
恢复演练的逻辑备份保留ACL，另外验证函数搜索路径、执行权限和不可变触发器。
这只是测试副本权限，不表示生产角色已调整或已有部署证据。
