# 体彩跨玩法比赛身份

本批为五赛季回填的第二个本地开发切片，尚未提交、部署或生产导入。第一批多季保留见 [official-season-retention.md](official-season-retention.md)。

同一真实比赛可同时进入竞彩足球、14场胜负彩、任九、6场半全场和4场进球。没有竞彩编号的传统足彩比赛，也应能保存和关联。禁止为满足原有外键而伪造竞彩行。

## 结构与边界

| 结构 | 职责 |
| --- | --- |
| `football_fixtures` | 只提供共同身份，不再复制比分、球队、赛季、赔率或预测 |
| `football_fixture_source_links` | 来源、ID体系、原比赛ID到共同身份的绑定，保留首次关联依据 |
| `football_pool_issue_matches` | 沿用现有玩法期次/场序，新增`fixture_id`、`identity_status`、证据及单行原材料；原`match_id`仍专指竞彩FK |
| `football_pool_fixture_revisions` | 自动保存不同版本的对阵/关联/原材料，包括首次刷新前的旧行；相同材料不重复增加版本 |
| `football_pool_fixture_catalog` | 读取四种传统玩法的全部当前成员，不要求竞彩FK；每条是玩法成员，比赛去重必须显式按`fixture_id` |

全部位于原有PostgreSQL，不另建业务数据库。119/118中的已发布历史和参考批次不改。29迁移曾创建的`official_season_matches`已被31删除，本批不假定该表仍存在，也不重建旧目录。现有`event_match_catalog`、模型输入、投注分析和账务准入不扩展；建立共同身份不代表传统足彩独有比赛已能生成模型预测。

## 关联规则

- `traditional.infohubMatchId`限定传统接口的明确字段；`jc.matchId`来自独立核验到的竞彩行。数值一样不能跨体系直接连接。
- 传统接口的通用`matchId`缺少跨玩法/期次全局身份依据，因此使用`traditional.<game_type>.<issue_no>.matchId`。同时有两个字段时全部保留，不能只保留优先的数字而丢失类型。
- 仅在联赛、主客名称、开球时刻完全一致且候选唯一时辅助跨体系连接；不做日期相近、名称模糊、主客颠倒的自动匹配。旧52迁移按同日选最新的逻辑不复用。
- 旧`TIMESTAMP`赛程字段表示北京时间墙上时刻；带偏移的输入先转为业务时区，再写无偏移字段。连接时区变化不应改变匹配结果。
- 明确来源绑定支持改期后沿用原身份。来源绑定互相冲突、同一体系出现另一个ID、球队或联赛矛盾时标记`conflict`，不更改旧绑定。首次材料缺名时，后续完整修订同样成为冲突检查依据。
- 缺少带类型的来源ID且没有唯一竞彩候选、旧期次未核实玩法来源等情况标记`pending`，仍保存材料。旧未分类`source_match_id`不擅自提升为带类型的ID。
- 共同身份、来源绑定和修订不可更新、删除或截断。自动过程不合并两个已经建立的身份；需要人工核实的映射修正留待明确修复流程。

`linked`只表示这条材料按上述规则已关联，不证明真实五季覆盖完整、规范球队已匹配、赛季归属已核实或比分为90分钟结果。源站别名/ID语义仍需真实材料核验，不能把固定样本通过当成来源正确性的证明。

## 场次和修订

14场和任九均需14场候选，任九不是只存9场；半全场是6场实际比赛，进球彩是4场。12/8等展开结构在没有证据支持折叠规则时，`total_matches`留空，原行仍保留并标`unverified_slot_layout`，不创建共享身份。数量符合但明确来源ID重复时标`duplicate_fixture_slots`。半全场/进球玩法的结果槽和`3+`等档位本批不解释为真实比分。

替换某一期某场时，当前行更新，旧身份和旧材料保留在修订表。修订去重依据由数据库按JSONB材料内容计算SHA256；重复采集相同内容不增加不同版本数。修订时间是本机数据库实际记录时间，不能冒充历史首次发布时间。原材料完全相同后再次出现也复用已有材料版本，不提供逐次轮询日志。

所有新写入经现有`store_pool_issue`和`store_pool_issue_matches`，由调用方提交同一期次/批次事务。先取得事务级身份锁，再写期次及成员，统一锁顺序；SQL失败传播给调用方回滚，不吞掉错误或提交半个批次。多个玩法保留各自成员，共用身份；不复制另一玩法停售时间。

## 发布和后续

125是前向迁移，不更改原迁移。迁移新增表/列、索引/触发器及只读视图，不批量重写原竞彩、赛果、已存方案或已发布历史批次。旧成员默认`pending`，明确刷新时才关联并留存旧行。

迁移应在发布工具的事务中执行，设锁等待2秒、语句30秒上限；索引会读取现有期次成员表，不读取九百多万条历史明细。失败事务回滚，不留半套结构。发布前应暂停相关写入，124/125和兼容代码一起部署；已写新关联后回退旧代码不能维护这些新字段，应暂停写入并修复前进。生产权限、全库迁移和实际锁时长尚未验收。按用户要求不创建备份。

本地验证使用固定样本及独立loopback测试库，包含受限`fqp`角色写入、证据不可变、原业务方案、并发、回滚和锁超时。CI已接线，尚未推送运行。

下一批仍需逐赛事五个已完成赛季的官方边界/成员证据、传统玩法历史期次材料盘点，以及与119历史事实和规范球队/赛季的关联；之后才部署并试小批回填。当前采集仍是既有当前期入口，未新增五年历史遍历器，不宣称五季数据已齐全。
