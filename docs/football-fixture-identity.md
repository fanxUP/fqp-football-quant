新增`football_competition_season_sources`保存现有`competition_seasons`对应的官方赛事/赛季命名空间、计划起止和证据；新增`football_fixture_seasons`关联125的共同比赛。`football_fixture_season_catalog`只投影明确绑定，旧自然年/世界杯标签关系不自动成为可信归属。它们仍在原PostgreSQL，复用原赛事/赛季/比赛，不复制历史事实。

全局`seasons`的旧日期/名称保持原样；新建赛事专用季时全局日期留空，权威计划日期取赛事来源关系。计划边界不是实际首末开球，也不是逐场归属证明：延期到范围外但有明确来源成员仍可接收；只有日期/名称相近不创建成员。旧119事实和已冻结模型不变，尚未接入训练。

操作入口`python -m scripts.football_season_identity --input material.json`默认离线预览，不连接数据库。`--mode rehearse`执行真实DML后回滚，`--mode apply`单次提交，使用显式环境`DATABASE_URL`。单批最多500个已存在的共同比赛；没有自动重试、后台采集或定时导入。事务失败调用方必须回滚；CLI始终回滚未提交内容并关闭连接。

输入含`competition_code`（已有规范代码）、`season_code`（赛事专用代码，如`premier-league:2024-2025`）、`season_name`、`boundary_document`、`member_documents`、`members`。每份document保存`url`、带时区的`captured_at`、原始字符串`body`及其UTF-8字节`sha256`；边界取官方uniform联赛`getMatchResultV1.qry`的`seasonStartDate/seasonEndDate`，不可误取查询`startDate/endDate`。每个member为`fixture_id`、`jc_match_id`，必须有同一来源赛季的明确逐场证明，并与已有125 `sporttery/jc.matchId`绑定一致。

`member_documents`支持两种官方原文：联赛响应的逐场`gmMatchId`，以及`getMatchHeadV1.qry?source=web&sportteryMatchId=...`详情。详情必须回显相同的`sportteryMatchId`、明确的`uniformLeagueId/seasonId`及有效`uniformMatchId`；赛事和赛季必须与边界来源一致，重复/缺失查询参数、其他域名或无时区采集时间均拒绝。详情证明按`explicit_match_head`记录，不伪称包含`gmMatchId`，也不能作为边界文档。每批最多60份成员原文、500个已存在共同身份；逐场详情宜分50场一批。采集时间是本次取证时间，`historical_prematch_eligible=false`，不会把历史排名作为赛前特征。这样旧季联赛接口不再提供成员列表时，仍可逐场核实，不靠日期猜归属。

仅边界响应允许无成员；传统独有场次不能伪造JC ID，应在另一个有明确来源证据的适配器接入。

写入详情证明前，还双向核对已有`sporttery/uniformMatchId`绑定：该统一比赛ID不能指向别的fixture，该fixture也不能已有另一个统一比赛ID。同一JC的所有详情必须给出相同的统一比赛ID；混合联赛和详情原文时保留详情证明，不因文档顺序漏查已提供的身份矛盾。没有这种来源绑定时仍可接受明确的JC证明，不因此虚构或自动补写统一比赛ID；已知冲突则拒绝，避免把身份矛盾带入赛季目录。

同批选中的不同fixture不能共用一个详情统一比赛ID，跨批也核对127中已记录的详情证明。该查询沿用127导入器串行锁及8秒超时，不合并取消后重售的竞彩条目，不创建新来源绑定；冲突留待逐场核实。

SHA和URL用于保留和校验材料，不独立证明官方真实性或人工选择的规范赛事映射；生产操作仍需复核真实来源及规范目标。旧官方边界响应有时不回显赛事/季ID，此时保留`binding_basis=request_parameters_only`与空的`response_id_echo`，只作计划边界证据；不冒充响应回显或逐场证明。逐场响应必须同时回显赛事和季ID且与查询一致。复用规范季前检查名称一致且未被另一赛事使用，错误旧行拒绝接入，不自动修名。证据一律标记历史赛前不可用。新关系禁止UPDATE/DELETE/TRUNCATE，已有错误或来源修订应先停止消费并核对引用，不能自动覆盖。数据库约束也校验逐场来源指向同一个fixture；受限fqp仅获得新表SELECT/INSERT及序列用量，不获得旧来源表UPDATE权限。导入函数拒绝autocommit连接，保持整批原子性。

本地验证采用独立loopback测试库和真实08/125/127迁移，覆盖受限fqp、回滚、幂等、冲突、来源命名空间、并发锁、不可变性和旧行保全。生产发布按固定127 SQL摘要及真实CI、DDL/ACL/业务回滚证据执行，遵照用户要求没有备份；不能把这324条成员当成五季全量验收。

### 赛事中心赛季筛选（本地实现，尚未发布）

沿用现有赛事中心与三个认证GET：`/api/league-data/catalog`、`/api/league-data/seasons/{id}`、`/api/league-data/seasons/{id}/fixtures`。可选`dataset=verified`读取已核实的竞彩归属；省略或`reference`继续原联赛资料批次，二者不拼接。页面“数据范围”切换清空原赛季、轮次、球队、页码和状态；URL保存范围、规范赛事代码、赛事季ID与筛选，切换时独立卸载旧资源，迟到响应不会串入新范围。

verified目录读取127官方联赛来源，保留只有计划边界的零成员赛季；不展示旧自然年/世界杯关系、不按当前日期猜赛季。赛程必须经127明确成员→125`sporttery/jc.matchId`→真实`official_matches`；同号其他命名空间、仅同日同名或只有来源季文字均不能加入。延期到计划边界外仍保留；0场表示本库当前未有合格成员，不等于来源没有比赛。此入口仅竞彩子集，不代表全联赛或传统玩法并集。

分页20默认/100上限，状态筛选及精确总数在数据库执行；只返回该页，固定按开球时刻/共同fixture ID排序。verified是当前共享目录读取，不冒用联赛批次快照，拒绝`batch_id`/轮次/规范球队筛选；参考资料的原批次固定分页保留。verified未提供完整联赛统计、积分榜、球队规范ID或实时阵容，返回未知/空而非由部分比赛计算；球队名称从官方事实投影且ID为null。只有`confirmed`且双方非负数字比分才展示赛果，缺失公布时间保持未知；采集或浏览时间不作为数据截止时间。

## 结构与边界

| 结构 | 职责 |
| --- | --- |
| `football_fixtures` | 只提供共同身份，不再复制比分、球队、赛季、赔率或预测 |
| `football_fixture_source_links` | 来源、ID体系、原比赛ID到共同身份的绑定，保留首次关联依据 |
| `football_pool_issue_matches` | 沿用现有玩法期次/场序，新增`fixture_id`、`identity_status`、证据及单行原材料；原`match_id`仍专指竞彩FK |
| `football_pool_fixture_revisions` | 自动保存不同版本的对阵/关联/原材料，包括首次刷新前的旧行；相同材料不重复增加版本 |
| `football_pool_fixture_catalog` | 读取四种传统玩法的全部当前成员，不要求竞彩FK；每条是玩法成员，比赛去重必须显式按`fixture_id` |

全部位于原有PostgreSQL，不另建业务数据库。119/118中的已发布历史和参考批次不改。29迁移曾创建的`official_season_matches`已被31删除，本批不假定该表仍存在，也不重建旧目录。现有`event_match_catalog`、模型输入、投注分析和账务准入不扩展；建立共同身份不代表传统足彩独有比赛已能生成模型预测。

## 关联规则

- `traditional.infohubMatchId`限定传统接口的明确字段；`jc.matchId`来自独立核验到的竞彩行。数值一样不能跨体系直接连接。
- 传统接口的通用`matchId`缺少跨玩法/期次全局身份依据，因此使用`traditional.<game_type>.<issue_no>.matchId`。同时有两个字段时全部保留，不能只保留优先的数字而丢失类型。
- 仅在联赛、主客名称、开球时刻完全一致且候选唯一时辅助跨体系连接；不做日期相近、名称模糊、主客颠倒的自动匹配。旧52迁移按同日选最新的逻辑不复用。
- 旧`TIMESTAMP`赛程字段表示北京时间墙上时刻；带偏移的输入先转为业务时区，再写无偏移字段。连接时区变化不应改变匹配结果。
- 明确来源绑定支持改期后沿用原身份。来源绑定互相冲突、同一体系出现另一个ID、球队或联赛矛盾时标记`conflict`，不更改旧绑定。首次材料缺名时，后续完整修订同样成为冲突检查依据。
- 缺少带类型的来源ID且没有唯一竞彩候选、旧期次未核实玩法来源等情况标记`pending`，仍保存材料。旧未分类`source_match_id`不擅自提升为带类型的ID。
- 共同身份、来源绑定和修订不可更新、删除或截断。自动过程不合并两个已经建立的身份；需要人工核实的映射修正留待明确修复流程。

`linked`只表示这条材料按上述规则已关联，不证明真实五季覆盖完整、规范球队已匹配、赛季归属已核实或比分为90分钟结果。源站别名/ID语义仍需真实材料核验，不能把固定样本通过当成来源正确性的证明。

## 场次和修订

14场和任九均需14场候选，任九不是只存9场；半全场是6场实际比赛，进球彩是4场。12/8等展开结构在没有证据支持折叠规则时，`total_matches`留空，原行仍保留并标`unverified_slot_layout`，不创建共享身份。数量符合但明确来源ID重复时标`duplicate_fixture_slots`。半全场/进球玩法的结果槽和`3+`等档位本批不解释为真实比分。

替换某一期某场时，当前行更新，旧身份和旧材料保留在修订表。修订去重依据由数据库按JSONB材料内容计算SHA256；重复采集相同内容不增加不同版本数。修订时间是本机数据库实际记录时间，不能冒充历史首次发布时间。原材料完全相同后再次出现也复用已有材料版本，不提供逐次轮询日志。

所有新写入经现有`store_pool_issue`和`store_pool_issue_matches`，由调用方提交同一期次/批次事务。先取得事务级身份锁，再写期次及成员，统一锁顺序；SQL失败传播给调用方回滚，不吞掉错误或提交半个批次。多个玩法保留各自成员，共用身份；不复制另一玩法停售时间。

## 后补竞彩与已发布历史资料

历史批次导入时没有竞彩行，其`official_match_id`会保持空值。后来回填竞彩后，不能更新已发布批次或重新复制明细来补这个外键。受控导入调用`link_official_history_fixture`，使用125既有身份表追加`sporttery/jc.matchId`与`titan007/matchId`的绑定；传统玩法与历史关联复用同一套绑定冲突处理。

入口核验原批次已发布、Titan原材料中只有目标竞彩ID、主客名称方向精确对应、北京时间开球时刻完全相同，以及双方确认比分一致。旧外键已指向别的竞彩、多个竞彩ID、改期/退款未核实等均不自动关联；已有不同共同身份不自动合并。原批次、球队映射、来源赛季文字、比分和明细不修改，不将采到时间补成历史公布时间。锁和写入由调用方事务控制，无内部提交；读取原始竞彩/赛果使用行共享锁，运行角色需要这两张原业务表的SELECT及至少一列UPDATE权限，历史表仍只需SELECT，身份表沿用125的SELECT/INSERT权限。

现有`/api/matches/{match_id}/history-reference`同时使用旧外键及上述明确来源绑定寻找已发布Titan资料，不增加接口参数；后续只追加上述可空赛季元数据。最新批次和指定批次分别读取；同批次多候选、旧外键与共同身份矛盾或来源ID格式异常返回`ambiguous`且不返回明细。来源名称和ID体系必须分别匹配，不能把不同网站的相同数字直接连接；统计及分页始终限定所选批次和比赛。

此历史关联本身不赋予历史赛前可见资格，不证明90分钟结果范围、规范赛事赛季、球员身份或模型训练链路已验收。规范赛季需另有127逐场成员证据。正式小批操作另存材料清单、真实事务回滚和实际HTTP读取证据；纯解析dry-run不能代替数据库预演，普通页面请求也不触发自动关联写入。

## P136：实际比赛赛果事实层（已部署）

迁移130新增football_fixture_result_facts，用于保存已绑定共享fixture的来源赛果观察。它与official_results及traditional pool期次的source_*结算字段分开；不会改写官方竞彩结果或体彩结算。每条观察保留来源名称、ID体系、来源比赛ID、实际比赛日期/时间精度、状态、比分依据、比分时段、半场/全场比分、解析来源载荷、证据和数据库生成的摘要。同一来源载荷只有在解析事实与证据完全一致时才按幂等重放；同一载荷对应不同比分/日期或证据会明确拒绝，来源载荷修订则追加新行。历史观察不可更新、删除或截断。

状态包括completed、shortened、abandoned、postponed、cancelled、awarded和unknown；比分依据包括on_field、awarded和unknown；比分时段包括regulation、extra_time、penalties和unknown。模型候选视图只包含实际比赛日期已知、明确completed、on_field、regulation且全场比分完整的观察。缺少实际比赛日期时只能保留为来源事实，不能进入模型；只写“完场”但没有证据证明比分时段的历史来源必须保留unknown，也不能自动进入模型。缺少精确开球时刻或来源发布时间时保持空值。

部署迁移只建空表，不回填Titan或其他来源数据。实际结果批次需重新核实同一fixture的来源链接、赛事状态和比分语义；禁止把判罚比分、延期旧排期比分或中止比分写成体彩结算赛果。
