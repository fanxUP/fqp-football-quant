# 多 Agent 模块实施计划与验收

## 范围

本次完成多 Agent 阶段 A：基础 Agent 框架。目标是让 Agent 注册、任务状态、审计、任务产物、人工审核和 AI Job Run 在本地 PostgreSQL 中形成可验证闭环。

本次不自动执行生产推荐、不修改预算规则、不删除生产数据，也不引入 Redis/Celery。长期任务仍由本机 Scheduler/Worker 执行，Codex 只负责开发、审查和受控触发。

## 当前差距

- Agent 注册、任务创建、审计和人工审核已有存储层，但任务状态没有统一合法迁移约束。
- `agent_task_artifacts` 已建表，但缺少可复用的登记/查询接口。
- 任务执行缺少统一 CLI，无法用一个命令创建任务、推进状态、登记产物和写入测试结果。
- 阶段 A 缺少可运行验收：L4/L5 审核闸门、状态迁移、审计日志、产物引用和 Job Run 都要有测试。

## 实施切片

### 切片 1：任务状态机

- 定义文档中的状态集合和合法迁移。
- 非法迁移返回失败，不修改数据库。
- 每次合法迁移写入审计日志。

### 切片 2：任务产物

- 支持登记文件、测试报告、数据报告等产物。
- 产物保存路径、摘要、哈希和元数据。
- 支持按任务查询产物。

### 切片 3：Agent CLI

- `list-agents`：查看启用 Agent。
- `create-task`：创建任务并按 L4/L5 自动创建审核闸门。
- `transition`：推进任务状态并记录审计。
- `add-artifact`：登记任务产物。
- `job`：记录 AI Job Run 的开始与完成。

## 验收标准

- [ ] Agent YAML 可加载并能同步到本地数据库。
- [ ] L4/L5 任务自动生成 pending 人工审核闸门。
- [ ] 非法状态迁移不会写入新状态。
- [ ] 合法状态迁移有审计记录。
- [ ] 任务产物可登记、查询，并保存 hash/metadata。
- [ ] AI Job Run 可记录 running、completed、failed。
- [ ] CLI 的所有写操作都要求明确 task_code/agent_name，并可追溯到数据库。
- [ ] 不触碰 Docker 部署，不自动发布正式推荐。
