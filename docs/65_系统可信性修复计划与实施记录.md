# 系统可信性修复计划与实施记录

更新日期：2026-07-13

## 目标

在保留现有架构和页面合并形态的前提下，修复真实运行态中影响多个板块的共同根因，使比赛、推荐、赛事档案、投注市场和系统监控之间形成可验证的业务闭环。

## 实施顺序

### 第一阶段：推荐与比赛状态

1. 实时推荐仅允许仍在售、未开赛、销售未截止、存在官方开放玩法和官方赔率快照的比赛。
2. 没有完整官方胜平负赔率时不再生成均匀赔率预测，也不再把合成赔率预测发布为实时推荐。
3. 已到开赛时间但赛果尚未回填的比赛统一显示为 `awaiting_result`，不得继续显示“待开赛”。

验收：接口测试先复现旧行为并失败；修复后 `/api/recommendations/live` 的 SQL 门槛完整，`/api/matches/active` 返回明确的待赛果状态。

### 第二阶段：赛事档案与系统入口

1. 赛事中心恢复 `official + supplemental` 全赛季档案。
2. 补充赛程显示“赛程补充”和“无官方编号”，且不能进入比赛详情、比赛中心或投注中心。
3. 后端面板接口返回稳定菜单分组；前端侧栏使用运行时分组，并把导航和主题切换改为键盘可操作元素。

验收：赛事页面测试覆盖两类来源；真实运行时侧栏能显示“系统监控”。

### 第三阶段：健康监控语义

1. 证据链或污染审计样本数为零时返回 `no_data`，不得判定 Stage 8 通过。
2. 健康快照对零样本进行降级，避免假绿灯。
3. 系统监控顶部总状态优先使用运维健康状态，基础 `/health` 只表示 API 可响应。

验收：后端 API 测试覆盖零样本；前端测试覆盖 `degraded` 顶部状态。

### 第四阶段：投注玩法市场

1. 校正体彩 `poolList`、官方玩法和赔率快照之间的映射。
2. 对当前可售比赛执行真实查询，确保开放玩法至少返回一组可选择赔率；没有市场时清晰显示数据未就绪。
3. 验证“选择 → 组合计算 → 模拟票据”接口链路，不创建未授权的真实票据。

验收：模拟器 API 测试通过，并用本地数据库完成只读接口验证。

## 全量回归门槛

- 后端全量 Pytest 通过。
- 前端全量 Vitest、TypeScript 类型检查和生产构建通过。
- Ruff 与 Mypy 通过。
- 本地真实 API 不再返回已开赛或已结算的实时推荐。
- 浏览器检查赛事中心、投注中心和系统监控无控制台错误。

## 不在本轮执行的事项

- 不全面重写前端视觉体系。
- 不删除历史文档或历史数据。
- 不把第三方补充比赛提升为体彩官方比赛。
- 不创建或提交真实投注。
