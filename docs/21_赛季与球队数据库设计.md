# 21 赛季与球队数据库设计

## 1. 设计目标

赛季与球队数据库是多维预测系统的长期基础库。它解决以下问题：

- 每个赛季有哪些赛事、阶段、规则；
- 每支球队属于哪个赛事赛季；
- 当前积分、排名、争冠、保级、晋级压力如何；
- 球队长期画像如何变化；
- 球队名称在不同数据源中如何映射；
- 历史推荐是否能够重建当时的赛季环境。

数据库必须遵循快照原则：积分榜、球队赛季画像、球队战力评分不能只保存最新值，而要保存不同时间点的快照。

## 2. 核心实体关系

```text
seasons
  -> competition_seasons
      -> season_standings_snapshots
      -> team_season_profiles
          -> player_season_profiles
          -> team_squad_snapshots
```

`teams` 是稳定主数据；`team_season_profiles` 是某支球队在某个赛季的画像；`season_standings_snapshots` 是某个时间点的积分榜状态。

## 3. seasons：赛季主表

用途：统一管理 2025-2026、2026、2026-2027 等不同时间制的赛季。

关键字段：

- `season_code`：唯一编码，如 `2025_2026`、`2026`；
- `start_date`、`end_date`：赛季起止；
- `is_current`：是否当前赛季。

落地规则：

1. 国内联赛通常使用跨年赛季或自然年赛季，要统一编码。
2. 世界杯、欧洲杯等国家队赛事可以作为独立 season。
3. 每场比赛必须尽量关联到 `competition_season_id`。

## 4. competitions：赛事主表

赛事类型建议：

```text
domestic_league      国内联赛
domestic_cup         国内杯赛
continental_cup      洲际杯赛
international        国家队赛事
friendly             友谊赛
```

字段说明：

- `is_league`：是否联赛；
- `is_cup`：是否杯赛；
- `has_group_stage`：是否有小组赛；
- `has_knockout_stage`：是否有淘汰赛；
- `level`：赛事层级，可用于联赛强度修正。

## 5. competition_seasons：赛事赛季表

每个赛事每个赛季必须独立建档。例如：英超 2025-2026、英超 2026-2027、欧冠 2025-2026 都是不同记录。

需要记录：

- 参赛队数量；
- 总轮次；
- 晋级名额；
- 降级名额；
- 欧战/洲际赛资格名额；
- 排名规则；
- 积分规则；
- 是否存在附加赛。

`ranking_rules` 必须使用 JSON 保存。原因是不同赛事排名规则不同，关系到小组排名、净胜球目标和赛制博弈。

示例：

```json
{
  "order": [
    "points",
    "goal_difference",
    "goals_for",
    "head_to_head_points",
    "head_to_head_goal_difference",
    "fair_play",
    "draw_lots"
  ]
}
```

## 6. season_standings_snapshots：积分榜快照表

用途：在任意推荐时间点重建积分环境。

必须保存：

- 排名；
- 场次；
- 胜平负；
- 进失球；
- 净胜球；
- 积分；
- 主场积分；
- 客场积分；
- 争冠压力；
- 欧战/晋级压力；
- 保级压力；
- 无欲无求评分。

战意评分不应该凭主观判断，而应该由积分形势推导：

```text
争冠压力 = 与榜首/冠军区积分差 + 剩余轮次 + 对手难度
保级压力 = 与降级区积分差 + 剩余轮次 + 净胜球劣势
晋级压力 = 当前排名与晋级线距离 + 小组赛剩余场次
无欲无求 = 已无法争冠/晋级且无保级压力
```

## 7. teams：球队主表

只保存稳定字段，例如：

- 官方名称；
- 中文名；
- 英文名；
- 城市；
- 国家；
- 建队年份；
- 主场球场；
- 官网。

不要把赛季身价、阵容、战术风格放在 `teams` 表中，因为这些会随赛季变化。

## 8. team_aliases：球队别名表

这是数据治理的核心。中国竞彩网、英文数据源、球队官网、第三方 API 对同一球队命名可能不同。

示例：

```text
中国竞彩网：曼城
英文数据源：Manchester City
别名：曼彻斯特城
缩写：Man City
```

每个别名都要保存：

- `source_name`；
- `alias_name`；
- `confidence`；
- `is_verified`。

未验证的球队映射不能直接进入正式推荐。

## 9. team_season_profiles：球队赛季画像表

这是本模块最重要的表。它表示一支球队在某个赛事赛季下的综合画像。

字段分组：

### 阵容规模

- 球员数量；
- 平均年龄；
- 外援数量；
- 国家队球员数量。

### 身价结构

- 球队总身价；
- 平均身价；
- 中位数身价；
- 前 5 身价；
- 理论最强 11 人身价；
- 替补深度身价；
- 联赛内身价排名；
- 联赛内身价分位。

### 强度评分

- 主场强度；
- 客场强度；
- 进攻强度；
- 防守强度；
- 中场强度；
- 替补深度。

### 教练与战术

- 主教练；
- 上任时间；
- 偏好阵型；
- 备选阵型；
- 战术风格。

## 10. 数据更新频率

| 数据 | 更新频率 | 说明 |
|---|---|---|
| 赛季/赛事规则 | 赛季初始化 + 规则变化时 | 人工校验 |
| 球队别名 | 持续更新 | 映射失败时人工处理 |
| 球队赛季画像 | 每周/每轮 | 身价、阵容、战术会变化 |
| 积分榜快照 | 每轮赛后 + 每日 | 战意计算需要 |
| 球队强度评分 | 每轮赛后 | 模型训练输入 |

## 11. 验收标准

1. 任意官方比赛能匹配到唯一主队和客队。
2. 任意比赛能关联到一个 `competition_season_id`，未知时必须标记 unknown，不得硬填。
3. 积分榜快照能重建推荐时的排名和积分环境。
4. 球队赛季画像有 snapshot_time，不能覆盖历史。
5. 球队别名映射失败时进入人工校对队列。
6. 战意评分必须基于积分榜快照，不得只写文本。
7. 赛季结束后数据冻结，不能被新赛季数据污染。
