# 共享请求治理（P103，分批交付）

## 当前状态

第一批提供 `scripts/request_quota.py` 内部原语；第二批已将 API-Football、NewsAPI、GNews、Guardian 的 HTTP 入口接入 `scripts/request_transport.py`。**源码已接入，真实账号尚未启用或核验**；没有生产配置变动、默认开账或默认额度。

第三批增加显式启用的请求规范化、账号权限/环境缓存隔离和跨任务请求合并；默认仍关闭复用。已有四个客户端自动使用同一发送层，无新私有数据库。网页/搜索后续复用该入口。整体 A103 仍待实际运行准入与独立审查，真实账号未激活。

## 客户端接入与显式配置

仅配置 API key 已不能发送。首次发送懒加载下列运维配置；缺失、格式错误、未核验、凭据不匹配、环境无分配或 Redis 故障均拒发，不访问业务库、不自动 provision。

- `FQP_REQUEST_QUOTA_ENVIRONMENT`：显式环境标识，必须存在于账号分配表。
- `REDIS_URL`：所有同账号消费者共同使用的协调 Redis；没有 localhost 回退。连接/命令超时各0.5秒，关闭Redis命令自动重试，每客户端连接池最多8连接。
- `FQP_REQUEST_QUOTA_CONFIG`：JSON对象，键为 `api_football`、`newsapi`、`gnews`、`guardian`。每条包含 `enabled`、`runtime_verified`、`credential_sha256` 和 `policy`。前两项必须严格为 true；摘要必须等于当前 key 的 SHA256；policy 为上述 QuotaPolicy 完整账号策略，provider 必须与条目键相同，environment_limits 使用 `[环境, 日分配]` 数组。

`runtime_verified` 是运维完成核验后的显式声明，**代码不会凭这个布尔值证明持久化、实际套餐或账号关系安全**。同账号多 key 的各进程可登记各自凭据摘要，但必须使用同一非秘密 account_scope、相同策略和同一 Redis；不得因轮换 key 创建新额度。摘要也作为敏感运维信息处理，不打印完整配置。

保持关闭的结构示意（数字为0，不能作为实际账号配置直接启用）：

```json
{
  "api_football": {
    "enabled": false,
    "runtime_verified": false,
    "credential_sha256": "<当前凭据的64位SHA256>",
    "policy": {
      "provider": "api_football",
      "account_scope": "verified-account-id",
      "daily_limit": 0,
      "minute_limit": 0,
      "environment_limits": [["development", 0], ["production", 0]],
      "day_reset_offset_seconds": 0,
      "minimum_interval_ms": 6100
    }
  }
}
```

首次启用仍需另行核验并显式开账；没有自动修复、在线重配或解除权限阻断命令。部署前先完成 A103 运行准入，否则现有可选采集会返回获取失败，已有本地数据不被该发送层清除。测试可显式注入内部账本；仅注入 HTTP client 不能绕过许可。

## 每次发送、错误与审计

- 默认 API-Football 最多3次尝试；新闻默认1次，可显式设为1–3。仅 HTTPX 传输失败和408/499/500/502/503/504可能重试；每次重新取许可，已有发送不退款。JSON损坏、错误业务包、其他4xx和3xx不重试。分页调用也逐次进入相同发送层，没有新增自动翻页。
- 端点限定为上述供应商地址，关闭重定向。401永久认证阻断；未识别为日耗尽的403永久权限/套餐阻断。API-Football token/subscription/requests/rateLimit、NewsAPI错误码、Guardian错误包和GNews错误数组不会被当作空结果成功。
- GNews只有明确包含当日额度和UTC午夜重置的错误消息、且策略日界为UTC午夜时，403才按日耗尽收紧；订阅失效或其他403保持阻断，避免把权限拒绝错误释放到下一天。
- API-Football日/分钟remaining分别使用 `x-ratelimit-requests-remaining` / `x-ratelimit-remaining`，只接收非负整数且只收紧。缺失/畸形头不增加额度。429和错误包rateLimit收紧当前分钟，并按Retry-After秒或HTTP日期设置共享冷却；缺有效值则60秒，冷却最多7天。供应商如果要求更长暂停，应关闭入口等待人工处理。503带冷却时不在本次逻辑请求内重试。
- 反馈写入失败不返回未经对账的成功，也不重发；已消费许可保持占额。原始HTTP异常/供应商错误文本不向外传递；HTTPX的INFO请求日志过滤查询参数中的凭据。不能据此承诺第三方自定义传输/额外日志处理器自动安全。
- `ApiFootballClient.call_count_today` 为兼容保留的本实例实际尝试计数，reset只清本地显示，不改共享账本；它不是账号当天用量。客户端诊断仅暴露发送数、状态码、剩余额度等，无原始参数/错误体/凭据。
- 新闻原审计表继续保存每个逻辑查询。返回 `requests` 仍为逻辑批次数，新增 `sentRequests`、`reusedRequests`、`blockedRequests`、`unmeasuredRequests`；cursor_state.transport记实际发送次数与是否量测。没有计数器的旧内部客户端标为未量测，不能假定发送1次。原历史审计计数不再作为发送许可；`planningDailyBudget` 是查询规划信息，`quotaSource` 标记共享账本，不伪造全账号已用量。单个逻辑查询可能有多次收费尝试，Redis是许可账本，审计不是逐次网络流水。
- 新闻发送发生在数据库连接上下文之外，存储/审计各自短连接；关闭本次拥有的HTTP/Redis客户端。其他API作业原有事务边界尚未在本批调整。

映射依据：[API-Football限流说明](https://www.api-football.com/news/post/how-ratelimit-works)、[NewsAPI错误码](https://newsapi.org/docs/errors)、[GNews错误处理](https://docs.gnews.io/error-handling)、[Guardian接口文档](https://open-platform.theguardian.com/documentation/)。这些公开说明不证明当前账号套餐、许可用途或实际返回头已经验证。

## 唯一账号与环境分配

- 使用 P101 目录中的来源代码作为 `provider`；`account_scope` 是不含密钥的真实配额账号标识。多把 key 若属于同一受限账号，必须映射为同一个 scope；不能随 worker/任务/日期随机生成。
- Redis 键只由 provider/account_scope 决定，环境不生成额外总账。所有环境连接同一协调 Redis，并使用同一策略；不同环境每日分配之和不得超过全账号日总额。未分配的环境直接拒绝。
- 所有配置纳入策略摘要。同账号参数、分配、重置窗口或许可时长改变时，旧账本不会自动生成新额度，而是拒绝不一致策略。运营变更须核对当前使用量和剩余额度后另行设计安全更新流程；本批没有在线重配/解封命令。
- 日/分钟预算为本地保守硬上限，不等同供应商套餐权益。0 表示禁用；不默认超额付费。日总额上限10,000、环境最多16、许可最长60秒，是原语的资源界限；超过界限先评审而非绕过。

## 窗口与生命周期

Redis `TIME` 为唯一计时来源。日窗口为固定86,400秒，显式指定距 UTC 午夜的重置偏移；分钟窗口为 UTC 对齐60秒固定桶。**真实供应商的日界、滚动窗口、计费规则仍待账户证据核实**；如供应商采用不同机制，须在启用前增加对应约束。多进程最小发送间隔可作为额外保守限制。

1. 操作者根据已核验用量显式 `provision(daily_usage=各环境已用量, minute_usage=当前分钟已用量)`；必须列全环境，当前实现分钟用量不能大于日用量。未分配的外部消费也须计入同账号开账用量或预先扣除额度。不得盲填0。
2. 每次发送调用 `reserve`，先原子占用日、分钟、环境额度；普通请求不能消耗尚未释放的临场保留。临场保留计入总额，`priority=True` 仍受总额限制。
3. 临近一次实际 HTTP 发送调用 `mark_sent(token)`，原子检查许可有效期、全局冷却/阻断、供应商收紧上限与最小间隔；成功才可发送一次。该调用成功后，许可已消费。
4. 传输超时、响应损坏、发送进程崩溃及计费不明，均保持占额。每次重试或分页是新发送，取得新许可。一次许可不能重复消费。
5. 仅本环境有效、未消费许可可 `cancel` 退额；过期没有足够证据证明未发送，故不自动退额。跨日/跨分钟旧许可不能发送或抵扣新窗口。每次原子操作清理失效许可，配额计数继续保守保留。
6. `release_priority_reserve` 仅释放当天保留限制，不增加总额；新日恢复保留。该内部原语不是权限边界，未来调用方须限制谁能使用优先/释放操作。

`mark_sent` 与实际网络系统调用不能成为跨系统原子事务：成功后未实际发送可能浪费额度。调用方不得长期缓存已消费许可，应在同一同步发送路径立即调用传输；严格预算优先于自动退款。

## 共享反馈

`SendReceipt` 记录消费时的日/分钟及已发送序号。`apply_feedback` 只收紧上限，不因迟到/乱序响应或正数 remaining 恢复额度；以发送序号加剩余量形成保守上限，避免把后来仍在途的预留再次放行。旧窗口剩余量不进入新窗口。

- `daily_remaining` / `minute_remaining` 必须由适配器确认所属窗口及供应商语义，未核实字段不能随意传入。304 是否收费也归供应商规则，不能默认免费。
- `retry_after_ms` 只延长全账号冷却；没有默认等待/自动重试循环。适配器负责区分分钟429与日耗尽、解析秒数或 HTTP 日期；未来有界重试也逐次取许可。
- `authentication_denied` / `plan_denied` 持续阻断全部环境，跨日不会自动解除；当前映射见上文。未识别的拒绝不会靠自动重试获取权限。
- 反馈仅提供保守收紧，不能修复未纳入共同协调的其他程序消费。所有同账号消费者必须纳入协调或提供可信、不重叠的预算分配证据。

## 故障与恢复

账号状态是一个**无 TTL** 的 Redis 值。缺失、JSON/字段/计数损坏、意外 TTL、时钟回退、策略不一致和 Redis 故障均拒绝取许可；不降级为进程内计数、不自动开账、不直接发送。此原语不读取/改写足球业务库；采集调用方仍可返回已有本地事实及明确的获取失败状态。

启用真实客户端前必须核实持久化、禁淘汰、权限、备份/恢复及主从切换行为。Redis 重启可依赖其已验证持久化恢复，但丢失或过时副本可能失去已计费用量：必须停发，核实供应商当前窗口用量后人工恢复；单独的 `SET NX` 和 AOF 存在不等于所有故障模式都安全。

当前原语不自行验证 Redis 的 `appendfsync`/复制/磁盘策略，也未实现持久化事故探测或故障切换准入，因此不能脱离部署门槛直接接付费账号。不得把共享曲线缓存“Redis 失败后直算”的策略移入发送层。

## 本地证据与边界

固定样本在专用 `redis:7-bookworm` 容器验证；无外网、不发布端口、独立临时卷，开启 AOF/always 和 noeviction。包含真实独立进程竞争与干净 stop/start 后恢复；这不是断电、磁盘损坏、淘汰或主从故障切换演练。当前运行应用的 Redis/数据库未修改，未连接生产，也未调用供应商。

上段为第一批持久化证据；第二批另用独立无外网、无公开端口的临时Redis（tmpfs、未启用持久化）联验固定HTTP响应、并发发送、重试、反馈和拦截，不重复声称持久化恢复已重测。

测试通过 `FQP_QUOTA_TEST_REDIS_URL` 显式选择本批专用实例；没有该变量时 Redis 集成用例跳过，绝不读取应用 `REDIS_URL`。跳过不能记为该用例通过。测试报告记录源码摘要、容器镜像、命令和退出码。


## 第三批：请求身份、短缓存与跨任务合并

`RedisRequestReuse` 复用相同Redis，命中和等待不取发送许可。内部注入必须匹配同一个ledger实例、相同配额策略/账号、环境和凭据；仅修改permission_scope不能创建新额度。缓存是可重建的传输结果，不是公共事实库；业务事实、时点观测及完整批次仍归P104。

### 默认关闭与权限

在各供应商的 `FQP_REQUEST_QUOTA_CONFIG` 条目可附加：

```json
{
  "reuse": {
    "enabled": false,
    "retention_verified": false,
    "permission_scope": "approved-purpose-and-permission-revision",
    "ttl_seconds": 60,
    "wait_ms": 10000,
    "max_payload_bytes": 262144
  }
}
```

缺reuse或enabled严格为false时维持仅配额发送；其他畸形配置拒绝发送，不能静默关闭保护。启用须enabled和retention_verified严格为true，且由操作者确认账号、用途/消费角色、权限版本及响应留存条款。布尔声明不代替真实许可。运行进程按批准用途使用不同permission_scope；此内部标识**不是用户级RBAC**，服务端用途鉴权归P107。权限/凭据/环境变更需重建客户端，不能热改未重载的实例；额度仍是全账号共同账。

TTL为1–300秒（默认60），等待0–30000毫秒（默认10000），可缓存JSON体1–1048576字节（默认262144）。它们是资源上限，不是推荐的供应商留存/比赛新鲜度；实际启用值还须符合许可和比赛阶段。未实现过期兜底或自动批量翻页。

### 请求身份与时间

- GET按HTTPX实际序列化后的参数排序；字典顺序、整数1/字符串1等相同网络参数可复用。同名参数顺序、查询文本的大小写/空格保持，不做激进语义合并。
- provider/account配额策略、环境、凭据摘要、权限/用途版本、复用策略、端点、HTTPX准备的全部header（含默认头和Cookie）、默认及显式查询的日期/赛季/时区/分页、优先级进入SHA256摘要键。键不含明文查询/凭据；不同凭据保守不共享缓存，即使它们消耗同一个账号总额。
- 调用入口端点白名单/禁重定向保留；显式header/query中的凭据若与发送层凭据不一致，在发送前拒绝。按实际HTTPX build_request的结果构造身份，包含默认参数、默认header和Cookie。隐式auth流程可能在准备后修改请求，当前拒绝复用该调用，不静默绕过。客户端事件hook同样拒绝；响应若改变Cookie/实际请求身份，不把结果发布到原键，owner仍可取结果、等待者明确不可复用。每个复用实例只能绑定一个HTTPX客户端；复用实例和发送层都由一个顺序作业持有，跨任务共享通过Redis完成。
- 成功响应有 `reuse_status=fetched/cache_hit/coalesced/not_stored`，错误可标unavailable；每次新逻辑调用重新置零attempts_sent，不复制历史响应的remaining/状态码来重新反馈额度。
- `fetched_at_ms` 是初次响应完成发送/配额反馈后，在Redis发布复用结果的UTC毫秒时间，**不是供应商内容发布时间、精确网络到达时间或再次核验时间**。age_ms使用Redis时钟。命中不修改原时间、不延长TTL；只有新发送才能形成新结果时间。P104读取时还需原文发布时间/首次取得/入库等正式观测字段，不能把本字段代替完整as_of证据。
- 新闻既有cursor_state.transport保存允许列表内的复用状态、时间/年龄。reusedRequests仅计成功且实际发送0次的cache_hit/coalesced；既有requests仍为逻辑查询。其他敏感参数/正文不进入审计。

### 原子认领与未知发送

一个摘要键以Lua原子认领。running记录唯一token且**无TTL**；其他调用有界等待，共享成功结果或明确错误。owner成功/失败发布时必须核验token；失去owner不会覆盖别人的记录或补发。所有等待者先后验证配额账本存在、策略正常且无认证/套餐阻断；额度耗尽或限流时仍可读同权限的未过期成功缓存，不增加收费。

running超过120秒、时钟回退、等待超时均不接管、不再发送。进程硬中断后保留待核实记录，牺牲该请求的自动恢复以避免重复扣费；它不是永远运行的后台锁续期任务。真实运行必须监测这些无TTL记录的数量/年龄，并人工核实owner进程和供应商消费；本批没有自动删除、恢复或解锁工具。

只有明确成功包（API-Football response、NewsAPI ok/articles、GNews articles、Guardian ok/results）可存储。真实成功的空数组可复用，但不被重新解释为确认无伤停/无球员。失败通知最多留30秒，只有安全错误代码，无正文/异常/空事实。非预期成功结构、过大响应或含当前凭据回显时，owner仍拿到已合法取得的数据，标not_stored；等待者得到shared_result_not_reusable，不能自动补发。普通发送失败的等待者得到shared_request_failed。

Redis/账本丢失或损坏、写缓存失败均不直连绕过；未知发送不退款。成功缓存到期后可重新认领，失败通知到期后可重新尝试并重新取配额。缓存命中不检查当前日余额，但认证/套餐阻断依然禁止复用。

**不得运行中淘汰、flush或手工删除running键。** 这会破坏唯一owner假设，即使配额账本仍可能限制总额，也不能保证不重复查询。可清除/过期的是完成结果；完整清空须先停发并核实全部owner，随后从已有事实/合法新调用重建，不触碰业务历史。共同Redis的持久化/禁淘汰/一致主节点、时钟与权限仍是上线门槛；未证明任意灾难/故障切换下恰好一次。

本批测试继续使用专用无外网tmpfs Redis、固定HTTPX响应和已有镜像，包含线程/独立进程合并、逐次重试计费、隔离、过期与故障关闭；不运行付费/生产采集或新的持久化恢复试验。第三批测试若缺专用Redis变量会明确失败；早期配额/发送集成用例仍可跳过，因此交付必须核对无skip的实际结果。

## 第四批：真实运行准入

前三批的固定样本验证证明代码在所测条件下工作；启用真实账号还须逐项保存以下证据。`runtime_verified`、`retention_verified` 是操作者的准入声明，不能由程序根据Key存在、配置相同或一次PING自动设为true。未启用来源可以保持关闭，但不能据此把该来源的真实接入验收标成通过。

| 条件 | 必需证据 | 缺失时的动作 |
|---|---|---|
| 账号与所有消费者 | 同一实际账号的全部Key、程序/主机/环境清单和非秘密账号标识；人工补采与其他程序也计入 | 保持该来源关闭；不能每任务新建account_scope |
| 许可、窗口与计费 | 账号当前套餐/用途、日界/分钟或滚动窗口、重试/分页/304计费和已核验的响应头语义，注明核验时间 | unknown；公开文档和模板不是实际账号证明 |
| 环境分配和开账 | 每环境非重叠分配、当前日/分钟真实已用量、外部消费与未知在途请求的保守占额 | 不盲填0，不因缺账本自动provision |
| 共同协调 | 所有发送者连接同一可写主节点/同一逻辑库、使用同一策略；迁移期间旧版发送者已停发 | 仅本机URL相同不足以证明跨主机协调 |
| Redis恢复 | 目标实例实际持久化、磁盘/写入故障行为、恢复后的账本与running记录，故障时能先停发并重新对账 | 周期RDB或仅挂载volume不能证明近期计费用量不丢；AOF配置本身也不是恢复证明 |
| 禁淘汰和资源 | 实际noeviction、Redis/容器内存预算与磁盘余量、拒写报警及容量依据 | 不用maxmemory=0代替资源预算；内存不足拒写时保持故障关闭 |
| 访问边界 | 非公网暴露、专用凭据和受限网络/键范围，普通缓存维护不能flush/删除配额与running | default/nopass且全命令全键不是付费账本可接受的隔离证明 |
| 可选短缓存 | 实际响应留存/再利用许可、批准用途和permission_scope版本、符合条款的TTL/大小 | reuse保持关闭；不把权限范围标识当用户鉴权 |
| 不明owner | 有人负责监测无TTL running的数量/年龄，能核实进程、当前在途及供应商用量，记录处置证据 | 不接管、不按锁龄删除、不靠切换permission_scope绕过 |
| 精确版本与审查 | 候选文件摘要、对应测试和独立审查结果、实际部署镜像版本及关闭/回退步骤 | 源码通过不代表运行镜像已更新 |

Redis运行核验只读使用`INFO`、白名单`CONFIG GET`、脱敏ACL检查及有界`SCAN/TYPE/PTTL`；不读取响应正文或owner token。**`RedisQuotaLedger.snapshot()`会更新时间/窗口并写回状态，不是只读诊断。** SCAN不提供事务一致快照；零个匹配键不证明开账正确、历史消费为零或未知owner已安全结清。

### 受控启用顺序

1. 先审查精确候选和账号证据，确认既有模型/业务本地读取可用；选定一个获批来源和环境，不一次启用全部供应商。
2. 在独立环境验证拟采用的Redis配置和恢复流程，按实际目标重新核验权限、持久化/写入错误、禁淘汰、内存/磁盘与告警。修改共享Redis须另有变更与回退记录，不在只读核验中执行CONFIG SET或重启。
3. 停发该账号的所有旧/新发送者，等待并核实在途调用，记录供应商当前窗口消费和各环境归属。旧版客户端没有这套发送许可，不能与新版共用付费账号继续发送。
4. 确认账本不存在的原因及既有消费后，由获授权操作者显式开账；已存在账本不能删除重建来更换策略或解除阻断。开账与新发送之间不允许其他消费者继续消耗未协调额度。
5. 将相同策略、环境分配和凭据匹配配置安全提供给目标进程，凭据不进入仓库/日志。配置声明只有证据齐全才设true。先保持reuse关闭；如需它，再单独核验留存许可和未知owner处置。
6. 经单独授权的有界真实调用核对实际发送、反馈、账本和审计，重试也计入预算。运行成功、已完成开账和跨进程重建均分别留证，之后才逐步恢复其他已登记发送者；未实际验证不能标真实接入成功。

本批只交付核验和操作步骤，不执行上述启用、服务变更或真实请求。

### 故障、停用与回退

- 账本缺失/损坏、写入失败、回退副本或持久化状态不可信：先停发该账号全部消费者，保留现存账本和running；核实供应商用量、旧在途和恢复点后再制定恢复操作。不要把故障前的旧账本复制回来直接复发，已发送未知仍计入消耗。
- 401/403持续阻断按实际认证/套餐原因处理；不能等待跨日、清账或换scope解封。更换凭据/策略前同样先核对账号归属和当前消耗；本批没有在线重配/解封工具。
- 未知running：停止相关新发送、核实owner和真实请求结果，保存处置依据。仅看到进程不存在或记录很旧不足以证明未发送；不能直接DEL/FLUSH、切换用途/环境来补发。
- 回退应用版本仍须保持付费发送关闭，直到旧版消费者也被证明使用受控入口；旧镜像可能恢复旧的非原子限额。保留账本/未知owner及已提交足球事实，不清库或重新计算历史票据。
- 不把`reuse.enabled=false`当故障恢复开关：它会让后续请求改走直接的配额发送，不能据此处理尚未结清的owner。先停发并完成核实，才考虑有记录的配置变更。

当前实现没有自动持久化事故探测、自动owner恢复、远端开账工具或监测后台任务；这些操作不能在未获授权时由诊断脚本隐式执行。基础数据查询与可选来源的获取失败应分开呈现，缺来源不会伪造空事实。


## 第五批：可执行只读检查与共享账号收尾

```sh
python -m scripts.jobs.check_request_governance
```

由私密环境文件提供专用 `FQP_REQUEST_RUNTIME_REDIS_URL`，必须包含观察员用户名/密码；不要把URL或Key写在命令行、仓库或工单中。缺配置不读取应用 `REDIS_URL`，也不自动创建账本。返回JSON仅包含白名单指标、聚合数量和固定问题码；退出0表示本次有限观测未发现问题，1表示需要处理，2表示检查不完整/不可用。任何退出码都不授权启用账号，`activation_verified`始终为false。

只扫描复用命名空间，最多20页/200个去重键、COUNT提示50；SCAN不是事务快照，COUNT不是服务端响应字节硬上限，达到页/键上限明确标不完整。每条命令前检查5秒总期限，独立客户端连接/命令超时0.5秒且无自动重试（最终命令可越过总期限最多一个命令超时）。完成短缓存不读取正文；仅对当时无TTL的记录读取最多4096字节前缀并再次核对TTL，输出running/120秒以上或时钟异常/损坏的数量和最大年龄，不输出key、owner token或正文。并发完成时前缀可能已变为结果，只在内存解析并丢弃；不得将Redis调试响应日志暴露。数据不一致、权限拒绝、错误类型/损坏或检查失败不冒充“0个异常”。

观察员需要 `+info +config|get +acl|getuser +time +scan +pttl +getrange +ping +select`，只授予复用命名空间的读取；它可以读取配置/用户ACL元数据及复用前缀，属于可信运维身份，不能提供给页面、LLM或普通用户。应用发送身份需要共享账本/复用键上的 `+eval +get +set +pttl +time +ping +select`，禁FLUSH/DEL/配置/ACL和无关键。ACL无法区分同一Lua中的provision/运行action，且GET/SET/EVAL仍可改变获准键；应用身份是受信任的内部服务身份，不能声称具备用户级授权或可抵御凭据持有者恶意重置。正式用途鉴权归P107。
