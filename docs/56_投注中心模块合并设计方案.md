# 56_投注中心模块合并设计方案

## 1. 目标

将现有“模拟投注”“实票管理”“对抗竞赛”合并为一个统一的业务模块：**投注中心**。

当前最新口径：

- **投注台**：仅供本人使用，负责选号、OCR 识别后的投注确认、注数/倍数/票面金额/理论奖金计算。
- **彩票**：替代原“实票管理”，左右两栏展示“我的彩票”和“Agent 的彩票”，按日期归档所有模拟票、实票、Agent 推荐票。
- **比赛结果**：替代原“对抗结果/对抗竞赛”，只展示结算后的盈亏、ROI、命中与趋势视图。

投注中心不提供购彩、代购、出票、收款能力，只提供以下合规功能：

1. 像体育投注站点一样完成可视化选号、票夹、注数、倍数、过关方式、预计奖金的模拟交互。
2. 将票单按来源分为“我的”和“Agent”两个主体。
3. 支持“模拟票”和“线下实票记录”两种资金口径，且二者不能混账。
4. 每天赛果完成后自动结算票单，将收益、ROI、命中率写入对抗成绩。
5. 让投注、实票、结算、对抗不再是三个割裂页面，而是一条统一闭环。

## 2. 设计原则

### 2.1 一个模块，两个主体，三种票源

```text
投注中心
  ├─ 我的
  │   ├─ 我的模拟票
  │   └─ 我的实票
  └─ Agent
      ├─ Agent推荐票
      └─ Agent自动模拟票
```

票单主体用于对抗归因：

| 主体 | owner_type | 说明 |
|---|---|---|
| 我的 | user | 用户手动选择、手动录入或 OCR 识别的票单 |
| Agent | agent | 系统推荐、策略任务或 Agent 自动生成的票单 |

票单来源用于资金和审计口径：

| 来源 | ticket_source | 说明 | 是否真实资金 |
|---|---|---|---|
| 模拟投注 | simulator | 用户在投注台提交的虚拟票 | 否 |
| 实票记录 | real | 用户线下自购后录入/OCR 的记录 | 是，系统只记录不交易 |
| 推荐票 | recommendation | Agent 推荐候选票，可转模拟或绑定实票 | 否 |

### 2.2 统一体验，隔离账本

前端投注体验统一：比赛列表、赔率按钮、票夹、过关方式、注数、倍数、金额、最高理论奖金、确认按钮。

后端账本隔离：

- `simulator` 使用虚拟账户，下注时扣虚拟余额，结算时返还虚拟奖金。
- `real` 只记录线下自购金额和兑奖结果，不提供系统内支付。
- `recommendation` 是推荐证据链，不直接等于投注；需要转成模拟票或绑定实票后才进入收益统计。

### 2.3 结算是唯一入榜入口

对抗成绩不能从票单创建时计算，只能从 `ticket_settlements` 读取。

```text
官方赛果确认
  -> 票单全部比赛可结算
  -> 生成 ticket_settlements
  -> 更新虚拟/真实账本
  -> 写入 betting_competition_daily_results
  -> 刷新 Agent vs 我的 对抗榜
```

## 3. 新模块归类

建议将现有两个模块合并为一个核心闭环模块：

| 当前模块 | 当前页面 | 合并后 |
|---|---|---|
| 实票上传与复盘 | 实票管理、复盘分析 | 投注中心、复盘分析 |
| 模拟与对抗实验 | 模拟投注、对抗竞赛 | 投注中心 |

合并后注册表建议：

```yaml
- module_id: betting_center_module
  name: 投注中心
  category: core_loop
  required: true
  safe_disable: false
  depends_on: [recommendation_core]
  panels: [betting_center, review_center]
```

页面建议：

| panel_id | 名称 | 路由 | 职责 |
|---|---|---|---|
| betting_center | 投注中心 | `/betting` | 选号、票夹、我的/Agent、模拟/实票、对抗概览 |
| review_center | 复盘分析 | `/reviews` | 日/周/月复盘、错误归因、模型迭代 |

旧路由兼容：

| 旧路由 | 处理方式 |
|---|---|
| `/simulator` | 302/前端重定向到 `/betting?tab=bet-slip&mode=simulator` |
| `/tickets` | 重定向到 `/betting?tab=tickets&owner=user` |
| `/competition` | 重定向到 `/betting?tab=competition` |

## 4. 页面结构

投注中心首页采用工作台结构，不做营销页。

```text
投注中心
  顶部：今日投入、已结算收益、ROI、待结算票数、当前领先方

  左侧：比赛与盘口
    - 日期/赛事/开赛时间筛选
    - 玩法 Tab：胜平负、让球胜平负、比分、总进球、半全场、混合过关
    - 赔率按钮：点击加入票夹，再点切换选项

  右侧：票夹
    - 票单主体：我的 / Agent
    - 票单方式：模拟投注 / 录入实票
    - 过关方式：单关、2串1、3串1、M串N
    - 胆码、倍数、注数、金额、理论最高奖金
    - 确认模拟投注 / 保存为实票草稿 / OCR上传

  下方：票单与对抗
    - 我的票单：全部、待结算、已中奖、未中奖、需校对
    - Agent票单：推荐票、自动模拟票、已结算
    - 对抗榜：今日、自然周、近30天、累计
```

### 4.1 博彩网站式投注台交互

借鉴常见体育投注站点的交互，但保留合规文案：

1. 赔率按钮是主操作：显示选项名与 SP 值，选中态清晰。
2. 同一比赛同一玩法只允许一个选项；混合过关允许同一比赛不同玩法，但提交前给出风险提示。
3. 票夹固定在右侧或移动端底部抽屉。
4. 票夹实时展示：
   - 比赛数
   - 注数
   - 单注金额 2 元
   - 倍数
   - 总金额
   - 理论最高奖金
5. 提交按钮按模式区分：
   - `确认模拟投注`
   - `保存实票记录`
   - `保存为 Agent 模拟票`

## 7. 每日结算与对抗入榜规则

### 7.1 结算条件

票单进入结算必须满足：

1. 票单状态为待结算。
2. 票单所有比赛都有官方确认赛果。
3. 票单未在 `ticket_settlements` 中出现过。
4. 实票必须 `confirm_status = confirmed`。
5. `competition_eligible = true` 才计入对抗。

### 7.2 收益口径

```text
stake = 票单投入
gross_prize = 理论税前奖金
tax = 单票奖金超过 10000 元部分按 20% 计算
net_prize = gross_prize - tax
profit_loss = net_prize - stake
roi = profit_loss / stake
```

### 7.3 对抗归因

| 票单 | owner_type | 计入 |
|---|---|---|
| 我的模拟票 | user | 我的-模拟成绩 |
| 我的实票 | user | 我的-实票成绩 |
| Agent 推荐转模拟 | agent | Agent-模拟成绩 |
| Agent 推荐绑定我的实票 | user 为实际执行者，agent 记录推荐贡献 | 我的实票成绩 + Agent 推荐命中贡献 |

对抗榜展示两层结果：

1. **资金结果**：按实际执行者归属，避免把用户线下实票算成 Agent 资金收益。
2. **推荐贡献**：按推荐来源归属，用于评估 Agent 推荐质量。

### 7.4 每日快照

建议新增或复用对抗快照表，生成日维度结果：

| 字段 | 说明 |
|---|---|
| result_date | 比赛结算日期 |
| round_id | 对抗周期 |
| owner_type | user / agent |
| ticket_source | simulator / real / recommendation |
| settled_ticket_count | 已结算票数 |
| total_stake | 总投入 |
| total_net_prize | 税后总奖金 |
| profit_loss | 净盈亏 |
| roi | 当日 ROI |
| hit_ticket_count | 命中彩票数 |

## 9. 需要先修复的已知风险

1. `settle_tickets.py` 中模拟票派奖判断使用了 `ticket_all_won`，但当前段落实际变量是 `all_won`。
2. `settle_tickets.py` 中实票派奖判断使用了 `all_won`，但实票段落实际变量是 `real_all_won`。
